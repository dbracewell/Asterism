## Decision and behavior

Keep the FTS adapter in the chat domain and change its contract from executed
Python ID collections to composable, typed SQL selects. `SqliteFtsSearchIndex`
owns SQLite `MATCH` syntax; `chat/search.py` adds owned chat/project base selects
and workspace predicates before executing a shared count/page relation. General
and project scopes do not query project matches. No new generic search domain,
query framework, shared-domain dependency, compatibility path or migration is
introduced. `db/queries.py` and the external API/generated clients are unchanged.

Use a single owner-filtered, page-ID-filtered message query with `row_number()` to
choose the first matching message per chat. This preserves the existing snippet
semantics: all query terms match the aggregate FTS document, while the snippet
uses the earliest owned message containing any term, ordered by timestamp then
message UUID. An all-term title match takes precedence. Page metadata remains
owner-scoped; no snippet query runs for an empty or title-only page. Only
page-sized ID lists remain in application queries.

SQLAlchemy query composition preserves ownership checks outside the adapter,
even when a test adapter deliberately returns foreign matches. Exact counts and
page selection use the same relation and stable updated-time/kind/UUID ordering.
The existing real HTTP membership tests retain all/project/General search,
foreign-project denial and unauthenticated rejection. This work does not claim
that exact counts, FTS scans, sorting or window ranking cost only O(page size),
or impose byte limits on selected message bodies.

## Query-bound evidence

The [machine-readable measurements](us-34.1-query-bounds-2026-10-24.json) come from
SQLAlchemy cursor instrumentation in the regression tests. Each bucket grows from
24 to 1,205 rows: owned content matches in the selected scope, owned title matches
in another scope, and foreign title matches. The page size remains seven.

| Scope   | Matching result total, small → large | SQL queries | Maximum binds per query | Snippet queries |
| ------- | ------------------------------------ | ----------- | ----------------------- | --------------- |
| All     | 49 → 2,411                           | 5 → 5       | 10 → 10                 | 1 → 1           |
| General | 24 → 1,205                           | 4 → 4       | 10 → 10                 | 1 → 1           |
| Project | 24 → 1,205                           | 6 → 6       | 10 → 10                 | 1 → 1           |

Project scope includes its owned-project lookup. Other-scope and foreign rows
sort differently so filtering/pagination mistakes cannot hide behind identical
counts. Tests also check the second page, beyond-end pages, real-index mixed ties,
page-only snippet binds, timestamp/UUID snippet ties, terms split across messages,
literal underscores, punctuation/FTS-looking input and the ten-term cap.

The three scope regressions were run against the original `main` implementation
with the corrected dataset, and all failed the bind ceiling: 54–55 binds even at
24 rows per bucket. The new implementation was restored immediately afterward.
The tests use disposable SQLite storage with foreign keys enabled. The measured
runtime is SQLite 3.50.4; the documented supported baseline remains SQLite 3.45+
with FTS5 and window functions. No other search dialect is implemented.
