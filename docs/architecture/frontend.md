# Frontend

This guide explains how the Next.js app is put together: its routes and feature
folders, how it loads and changes server data, the layout and scrolling rules every
page follows, how the chat transcript is built, how settings are organized, the
in-app help system, and how the frontend is tested. Read it before adding a page,
a settings section or a chat component. Colors, type and other visual tokens are in
[themes](themes.md).

The frontend is Next.js 16 with React 19, Tailwind CSS 4 and shadcn/ui. This
version of Next.js differs from older ones; the docs bundled in
`node_modules/next/dist/docs/` are the reference
([`apps/frontend/AGENTS.md`](../../apps/frontend/AGENTS.md)).

## Concepts

- **Route groups.** `src/app/(auth)` holds the pages before sign-in: sign-in,
  first-run setup, invite and password reset. `src/app/(main)` holds the signed-in
  workspace. `src/app/e2e` holds test harness pages, which return 404 unless `ASTERISM_CONFIG_PROFILE` is `test`.
- **Feature folders.** Each product area has a folder under `src/features/` (chat,
  files, projects, settings, study, classes, canvas, help, theme and so on) with its
  components, hooks and helpers. Shared building blocks live in `src/components`,
  with the shadcn/ui primitives in `src/components/ui`.
- **The generated client.** `src/lib/client` is generated by Hey API from the
  backend's OpenAPI schema (`pnpm codegen`). It provides typed request functions and
  TanStack Query options for every route.
- **Server state lives in TanStack Query.** Pages never load or cache API data with
  `useEffect` or hand-written loaders.

## How it works

### Loading and changing data

Every backend call goes through the generated client and TanStack Query:

- **Reads** use the generated query options, such as
  `projectGetOneOptions({ client, path })`, with `useQuery`.
- **Writes** use the generated mutation options with `useMutation`. The shared
  mutation cache ([`lib/mutation-cache.ts`](../../apps/frontend/src/lib/mutation-cache.ts))
  invalidates the affected queries after every mutation, so individual mutations
  don't invalidate anything themselves.
- **Tokens.** The client asks Better Auth for a short-lived JWT and reuses it until a
  minute before it expires ([`lib/backend-token.ts`](../../apps/frontend/src/lib/backend-token.ts)).
  A 401 drops it; a 403 (signed in but not allowed) keeps it.
- **Interactive UI uses shadcn/ui components,** not raw HTML elements. A missing
  component is installed with approval rather than rebuilt by hand.

The chat stream is the one exception to request-and-response. `useChatWebSocket`
([`features/chat/hooks/use-chat-websocket.tsx`](../../apps/frontend/src/features/chat/hooks/use-chat-websocket.tsx))
holds the chat's socket and turns packets into state
([chat and WebSocket](chat-and-websocket.md)). Events such as new chat titles arrive
through a shared worker that listens to `/api/stream`.

### The app shell

`RootLayout` loads the theme on the server and applies its colors and the font-size
cookie to the root element, so the first paint is already themed ([themes](themes.md)).
`DashboardLayout` composes the signed-in workspace: the sidebar, the current-user
context, the help audience and the page.

The sidebar has the General and Projects lists, five items per page, each with its
own expand state stored in a cookie. The server reads those cookies and passes them
to the client components, so server markup and hydration agree.
[Project workspaces](project-workspaces.md) covers the sidebar and project pages in
detail.

On a phone, the header is a full-width sticky bar with a 44 px menu button. The
sidebar opens as a drawer that closes on navigation and returns focus to the button.

### Layout and scrolling rules

The page body never scrolls. Instead, each panel owns its scroll area, and the rules
below keep every control reachable at narrow widths, short heights, inside nested
panes and with text enlarged to 200%:

- **The shell** is bounded to `100dvh`. Its main area scrolls ordinary pages;
  specialized panels such as chat history and the file list scroll themselves.
- **Flex children shrink.** Columns use `min-h-0` and `min-w-0`, so content can
  shrink and the right element scrolls. Checking only `scrollWidth <= clientWidth`
  misses clipped vertical content, so tests check that controls are actually reachable.
- **The chat session** is two siblings: history, which scrolls, and the composer,
  which takes at most 60% of the height and scrolls its own contents (attached files,
  errors, long drafts). The composer can't cover the last message. Both share a
  64rem maximum width.
- **Rich content wraps or scrolls in place.** Prose and long tokens wrap. Tables, code
  blocks and long equations get their own keyboard-focusable horizontal scroll
  regions, and a code block's header (language, wrap toggle, copy) stays put while
  its body scrolls.
- **Settings.** `SettingsCard` watches its own width: below 640 px its section tabs
  become a horizontally scrolling strip, above it a vertical navigation column. The
  active section scrolls on its own.
- **Dialogs** are capped at `calc(100dvh - 2rem)` and scroll their whole content, so a
  long form never pushes its footer out of reach. A model picker inside a dialog opens
  inside that dialog, and Escape closes the picker before the dialog.
- **Containers, not viewports.** The theme editor, file lists and agent forms switch
  layout by their own container width, so they work the same in a narrow pane as on a
  narrow screen.
- **Sign-in pages** own a `100dvh` scroll area. Short forms are centered and tall ones
  scroll from the top. They declare `interactiveWidget: "resizes-content"` so a phone
  keyboard resizes the page instead of covering the form, and a form error takes focus
  and scrolls into view.

### The chat transcript

The transcript is built from small components in
[`features/chat/components/`](../../apps/frontend/src/features/chat/components/):

| Component            | Shows                                                                                                                                                                                                    |
| -------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `MessageItem`        | One message: the marker, body, meta line and actions. Each is an `article` named "Your message" or "Assistant message".                                                                                  |
| `MessageMeta`        | Stopped state, relative time and tokens per second. Hidden until hover or focus, always shown on touch. Times use the user's stored time zone.                                                           |
| `AgentTimeline`      | Reasoning (when Show thinking is on) and tool calls as one collapsible list, with a summary such as "Thinking · 2 tool calls · 1 failed". Arguments and results are plain text.                          |
| `ToolApprovalCards`  | A card per tool waiting for approval, with the arguments, an advisory risk hint and Approve or Deny. A new card takes focus unless the user is typing, and a live region announces how many are waiting. |
| `RetrievalCitations` | "Sources" as numbered chips, one per file, with a preview on hover or focus. A source no longer in scope shows as unavailable with a retry.                                                              |
| `StreamingIndicator` | Five twinkling stars with "Assistant is working…", still under reduced motion.                                                                                                                           |
| `AgentConstellation` | The live delegation graph: the main agent and each sub-agent as stars joined by lines, folding past 16 sub-agents into "+N more".                                                                        |
| `DelegationSummary`  | After a step that delegated, a collapsed line such as "3 agents · 12.0 s · 7 tools" that expands to the graph, the agents and their outputs.                                                             |

A few behaviors span them:

- **Jump to latest.** A pill above the composer appears when the reader is more than
  200 px from the bottom, or as soon as they scroll up during streaming, which also
  stops auto-follow.
- **Tool durations** are measured in the browser, from a call's `tool_call` packet to
  the `complete` that carries its result, so only calls watched live show one.
- **The delegation graph is accessible.** The drawing is hidden from assistive
  technology; an ordered list of buttons, one per agent, carries the names, models,
  states and who delegated, and opens one details region at a time. One polite live
  region announces "Researcher started." and "Researcher finished." once each.
- **Untrusted text stays text.** Messages render through `MarkdownViewer`, which
  follows the [content policy](markdown-content.md). Tool arguments, results,
  excerpts and file names render as plain React text.

### Settings

Settings is one page with two tabs, selected by the `t` URL parameter, and a section
within each, selected by `setting`. Changing section keeps other parameters. Sections
load lazily.

| User Settings                                                               | Admin Settings                                           |
| --------------------------------------------------------------------------- | -------------------------------------------------------- |
| General: appearance, Show thinking, default model, Canvas, account and data | Providers, Theme editor, Groups, Users, Usage, Status    |
| Your Asterism: About you and usage                                          | Tools, Skills, Canvas, ChatGPT Plans, Context compaction |
| Skills, Templates, Rubrics                                                  | Image generation, Image captioning, Educators, Export    |
| Agents: the main agent, sub-agents and the General chat set                 | Code execution (marked **Planned**)                      |
| ChatGPT: a personal plan connection                                         |                                                          |

The admin sections are defined in
[`admin-settings/lazy-sections.tsx`](../../apps/frontend/src/features/settings/ui/admin-settings/lazy-sections.tsx)
and the user sections in
[`user-settings/index.tsx`](../../apps/frontend/src/features/settings/ui/user-settings/index.tsx).
Code execution is the only planned section: its pane explains what is coming and
offers no controls. Admin Settings isn't shown to other users, but that is
presentation only; every admin route checks the role itself.

### In-app help

Help is written in the frontend, next to the features it describes
([`features/help/`](../../apps/frontend/src/features/help/),
[ADR-0032](../adr/0032-in-app-help-content.md)). There is no help database or admin
editor, so help changes in the same commit as the behavior it describes.

- **The registry** ([`registry.ts`](../../apps/frontend/src/features/help/registry.ts))
  holds every help entry under a typed ID: `concept.*` for glossary terms, and a
  surface prefix such as `settings.*` for one control. Each entry has a title, a
  one- or two-sentence summary, details shown after "Learn more", related entries and
  an audience (`everyone` or `admin`). TypeScript refuses a missing entry or an unknown
  ID.
- **Inline help.** `HelpIcon`, `HelpHeading` and the page header's `help` slot open an
  entry in a popover that works with touch and keyboard.
- **Page guides** ([`pages.ts`](../../apps/frontend/src/features/help/pages.ts)) give
  every page and settings section a guide: its purpose, its areas, common tasks and
  related terms. A test reads the route folders and settings lists and fails if a page
  or section has no guide.
- **The help center** at `/help` searches the glossary, control help and page guides
  together, and links to each entry by anchor.
- **The user guide** at `/help/guide` serves `docs/guide` for the installed version
  ([`features/guide/`](../../apps/frontend/src/features/guide/), US-90.9). Pages are
  read when requested, only from the files the folder lists, and rendered by the
  guide's own Markdown renderer, not the chat viewer. Links to other guide pages
  become routes, screenshots come from `/help/guide/images`, and links that leave
  the guide go to the repository. The image copies `docs/guide` to
  `/app/docs/guide`. Each page guide's `walkthrough` names its guide page, shown as
  "Read the full walkthrough"; a test checks every one resolves.
- **The first-chat tour** ([`tour.ts`](../../apps/frontend/src/features/help/tour.ts))
  highlights the composer's controls one at a time, skipping any that aren't on the
  page. New users are offered it until they finish or dismiss it, stored as their
  `first_chat_tour` setting, and `?tour=first-chat` starts it again.
- **Audience.** Admin-only entries render nothing for other users. The audience comes
  from the server-loaded role; it is presentation only.

Help describes only what is implemented. It must not suggest that skills, modes or
templates grant tools or files, that anything is remembered beyond the conversation,
or that a learning mode always behaves exactly as described; tests check several of
these statements.

The in-app help is short reference text. The user guide in `docs/guide/`
([EPIC-89](../epics/EPIC-89-USER-GUIDE.md)) is the step-by-step tutorial; it uses
the same names as the registry ([terminology](../terminology.md)).

### Icons and brand assets

Lucide is the only icon set. `LucideProvider` in
[`src/app/providers.tsx`](../../apps/frontend/src/app/providers.tsx) sets one stroke
width for every icon, so components set only size and color; a test refuses other
icon packages and per-icon stroke widths.

[`src/app/icon.svg`](../../apps/frontend/src/app/icon.svg) is the source of every
brand image. `pnpm --filter @asterism/frontend generate:icons` renders the favicon,
the iOS and web manifest icons, the maskable icon and the 1200×630 link-preview image
from it. `src/app/manifest.ts` serves the web manifest, and the root layout sets
`metadataBase` from `PUBLIC_URL` so preview images get absolute URLs.

### Accessibility and motion

- Controls that look like icons have accessible names, and icon buttons and sidebar
  actions are at least 24 CSS pixels, even at the smallest font size.
- Sidebar actions appear on keyboard focus as well as hover.
- `prefers-reduced-motion: reduce` turns off CSS animations, transitions and smooth
  scrolling. Status text stays, and nothing depends on an animation to be understood.
- State is never shown by color alone; text or shape carries it too.

## Testing

| Layer                 | Tool                                                                       | Use it for                                                 |
| --------------------- | -------------------------------------------------------------------------- | ---------------------------------------------------------- |
| Unit and component    | Vitest and Testing Library, next to the code (`*.test.ts(x)`)              | State, labels, parsing, layout helpers                     |
| Fixture browser tests | Playwright against `src/app/e2e/*` harness pages with mocked API responses | Stress cases: long content, narrow panes, keyboard, themes |
| Isolated end-to-end   | `node scripts/run-isolated-e2e.mjs`                                        | Real sign-in, backend and sockets in disposable storage    |

The isolated runner needs ports 3000, 3100 and 8000 free, creates and deletes its own
storage and never loads `.env`. Run Playwright with one worker, as CI does: in
parallel, the dev server's first compile of a route can reload other tests' pages.
Every Playwright case fails on a content-security-policy violation or an unhandled
page error, so the suite as a whole shows the app runs under the page policy.

Visual and contrast coverage across themes is described in the
[theme and layout review matrix](../reviews/theme-layout-review-matrix.md).

## Rules

- All server data goes through the generated client and TanStack Query; the shared
  mutation cache invalidates.
- Interactive UI uses shadcn/ui components.
- Each panel owns its scroll area, and every control stays reachable at 320 px wide,
  300 px tall and 200% text.
- Untrusted text (messages, tool data, excerpts, file names) renders through
  `MarkdownViewer` or as plain text, never as HTML.
- Hiding something in the UI is never an authorization check.
- Every page and settings section has a help guide, and help describes only what
  exists.

2. [`src/features/`](../../apps/frontend/src/features/): one folder per product area.
3. [`src/lib/client/`](../../apps/frontend/src/lib/client/): the generated API client.
4. [`src/lib/mutation-cache.ts`](../../apps/frontend/src/lib/mutation-cache.ts) and
   [`src/lib/backend-token.ts`](../../apps/frontend/src/lib/backend-token.ts): shared
   query behavior and tokens.
5. [`src/components/ui/`](../../apps/frontend/src/components/ui/): shadcn/ui primitives.
6. [`e2e/`](../../apps/frontend/e2e/): Playwright tests.
